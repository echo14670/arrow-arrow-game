## 详细过程

### 1. 环境勘测与技术选型

**我提出的要求**：先别写代码，检查本机能不能跑 Pygame，Python 版本、图形库、pip 网络情况都报给我。

**AI 的做法**：依次检查 `python --version`、`import tkinter`、`pip list`、`pip install --dry-run pygame`，
发现 Python 3.13.12 自带 tkinter 8.6、pygame 未安装但存在 `pygame-2.6.1-cp313-win_amd64.whl`；
随后真实安装时 pip 直连 PyPI 卡了十多分钟没进展。

**效果**：技术栈定为 Python 3.13.12 + Pygame 2.6.1，不引入 numpy 等其他依赖。

**我做的修改**：确认第 3 方依赖只有 pygame 一个；把安装命令换成清华镜像
`pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple`，
安装立刻完成（pygame 2.6.1 + pyinstaller 6.22.3）。

### 2. 任务要求解读与开发计划

**我提出的要求**：读作业要求，把评分点拆成可执行的任务，并给出仓库结构。

**AI 的做法**：把评分表拆成「界面与交互 / 路径判断 / 飞出与碰撞 / 关卡流程 / AIGC 记录 / 测试 / GitHub 与 README / 博客与 PSP」，
并设计出 `game/`（逻辑）+ `game/ui/`（界面）+ `tests/` + `tools/` + `docs/` 的分层结构，
关键是**把游戏规则与界面彻底分开**：`Session` 是纯逻辑状态机，界面只负责画和转发事件。

**效果**：逻辑可以脱离窗口做自动化测试，`tests/test_session.py` 里的 23 条用例全部不依赖 pygame 窗口。

**我做的修改**：在计划里补上「6 个关卡」「计时 / 撤销 / 打包 exe 三个扩展功能」，
并确认动画期间的输入锁行为。

### 3. 关卡可解性（这次最有价值的一次协作）

**我提出的要求**：随机生成关卡很容易产生死局，怎么保证每一关一定能通关？

**AI 的做法**：给出「逆向摆放」构造法：如果一关的消除顺序是 r1…rn，那么消除 r_i 时棋盘上还剩
r_i…rn，所以只要按 rn…r1 的顺序摆放，并且摆放每个箭头时它相对「已摆放的箭头」前方通畅，
构造出来的关卡就必然存在这条通关路径。同时写了贪心求解器 `solve()`：
因为拿走箭头只会让别的箭头更自由（可解性单调），所以不需要回溯，逐步贪心即可。

**效果**：`tools/generate_levels.py` 每次都能生成保证可解的布局，
`tests/test_levels.py` 断言「解序列长度 == 箭头数」，6 关全部通过。

**我做的修改**：第 1 关不用生成器，改成手写的 3 箭头教学关；
其余关卡按「开局被挡箭头数 / 可选步数」人工挑选手感更好的布局；
增加 `tools/level_stats.py` 输出每关统计，方便填 README 表格。

### 4. 路径检测的边界坑

**我提出的要求**：写四种方向的路径检测，注意别出现数组越界。

**AI 的做法**：实现为带边界判断的循环，并明确写下注释：
如果写成 `self._cells[row - 1][col]`，在 `row == 0` 时 Python 的负索引会绕到棋盘最下面一行，
把棋盘底部的箭头误判成阻挡——这正是「向上判断出现越界」这类经典 bug 的另一种表现。

**效果**：核心逻辑一次写对。

**我做的修改**：额外补了回归用例 `test_negative_index_wraparound_regression`：
棋盘左上角放朝上的箭头、左下角放朝上的箭头，断言左上角那个是畅通的、左下角那个被挡住。

### 5. 自动化测试：AI 写的测试自己也有 bug

**我提出的要求**：按作业要求的 T01–T06 写自动化测试。

**AI 的做法**：一次生成 51 条用例（后来加上界面冒烟测试共 58 条）。

**效果**：第一次运行：`Ran 51 tests ... FAILED (failures=3, errors=5)`。

**我做的修改**：逐条定位，发现三处都是**测试代码自己写错**，不是游戏逻辑错：

1. 测试用关卡 `PAIR` 的两行写成 `">."` 和 `"<.."`，行宽不同，`Board.from_grid` 直接抛异常；
   改成 `">.."` 后正常。
2. 「四个方向都要能被挡住」的用例把箭头放在棋盘边界上，而上/左两个方向的箭头前方本来就是
   棋盘外、必然畅通；改为在 3×3 棋盘中心程序化摆放箭头和阻挡物。
3. T06 的用例先点掉了唯一能解救受阻箭头的那个箭头，导致后面找不到「被挡住的箭头」；
   调整为先点被挡的箭头，再点畅通的箭头。

修正后 51 条全部通过；随后又补了 7 条界面冒烟测试，共 58 条。

### 6. 界面截图与视觉缺陷

**我提出的要求**：README 和博客要截图，但我没法一张张手动截。

**AI 的做法**：写 `tools/capture_screens.py`，用 SDL 的 dummy 视频驱动离屏渲染，
先把 session 推进到各个阶段（开始 / 游戏 / 碰撞 / 第 3 关 / 过关 / 失败 / 全部通关），
再直接把画面保存成 PNG。

**效果**：一次生成 7 张截图，而且截图本身暴露了两个我看不出来的问题。

**我做的修改**：

1. 碰撞提示文字「被挡住了！」正好压在箭头上，两者都看不清；把浮字起点从格子中心
   改成格子上方 6 像素，再向上飘。
2. 结果面板里第 4 行文字被「返回主菜单」按钮盖住；重新排布面板尺寸与按钮位置后重新出图确认。

顺带发现「全部通关」界面显示成「通关 7 / 6 关」——重复通关同一关被重复计数，
改成用集合记录已通关关卡后显示「通关 6 / 6 关」。

### 7. 打包成可执行文件

**我提出的要求**：作业允许把程序打包成 exe，帮我加上。

**AI 的做法**：给出 PyInstaller 参数
`--noconfirm --clean --windowed --onefile --name ArrowArrowGame main.py`，
并写成 `tools/build_exe.py` 一键执行。

**效果**：生成 `dist/ArrowArrowGame.exe`（约 27 MB），实测启动后持续运行正常。

**我做的修改**：可执行文件用 ASCII 名字，避免中文程序名在某些环境下的路径问题；
把 `build/`、`dist/`、`*.spec` 写进 `.gitignore`，只保留源码与一键打包脚本。

### 8. 增加「选择关卡」功能，并定位一次真实的进程崩溃

**我提出的要求**：在主菜单「开始游戏」按钮旁边再加一个「选择关卡」按钮和配套功能，
做完自己检查一遍。

**AI 的做法**：在 `Phase` 中新增 `LEVEL_SELECT`，把原来的 `start_game()` 重构成
`start_at_level(0)`，另加 `open_level_select()` 和 `start_at_level(index)`——
从指定关卡开始时把计时、点击、失误、撤销、已通关记录全部清零；
界面层增加一个整屏的选关面板：六行关卡，每行显示名称与「尺寸 · 箭头数 · 失误上限」，
鼠标悬停高亮，也支持数字键 1–6 直接开局。

**效果**：功能可用，但在自检跑测试时，进程在第二个「会绘制界面」的用例上直接崩溃，
退出码 `0xC0000005`（访问违例），而且这个用例单独跑是通过的。

**我做的修改**：先排除了业务逻辑问题（单独跑该用例通过、手动写脚本也正常），
再对比「单独跑通过、整包跑崩溃」的差别，锁定到重复的 `pygame.quit()` / `init()` 循环上：
`theme.load_font` 与 `arrow.arrow_surface` 用 `lru_cache` 把 pygame 的 Font 和 Surface
缓存了下来，`pygame.quit()` 之后这些对象引用的底层资源已经释放，
下一轮初始化后再拿它们绘制就会访问违例。修法是给两个模块各加一个 `clear_cache()`，
在 `Game.__init__` 里 `pygame.init()` 之后立刻调用，并补了一条回归用例
`test_survives_restarting_pygame`（绘制一次 → 退出 pygame → 新建 Game 再绘制）。
顺带把选关面板从「半透明覆盖在主菜单上」改成整屏面板，避免背后的标题透出半截。

### 9. 增加「自定义关卡」：让玩家自己定大小、箭头数和难度

**我提出的要求**：在选关界面六关下面再加一个「自定义关卡」入口，让玩家自己输入地图大小
（几×几，你帮我定一个范围保证界面不出问题）、初始箭头数量（大小定好之后自动算出理论上限、
下限 1 个）、难度（高/中/低三档，用 best_layout 衡量）；随机生成的关卡先用求解器保证有解，
再按难度挑候选；做完自动测试并提交。

**AI 的做法**：把功能拆成三层——

1. `game/generator.py`：候选生成与评分。参数范围定为 2×2 到 6×6（上限沿用界面里按 6×6
   设计的棋盘尺寸），箭头数量上限就是格子总数，下限 1；
2. `game/setup.py`：表单模型 `CustomSetup`，负责夹紧取值范围、在行/列变化后联动箭头数量上限；
3. `game/session.py` + `game/ui/screens.py`：新增 `Phase.CUSTOM_SETUP` 阶段，选关面板下面按
   「已有关卡数量」动态定位一个入口按钮，面板里是三行「− 数值 ＋」步进、三个难度按钮和生成按钮。

**效果**：功能可用，但过程中有三处需要我自己判断的问题：

1. **高密度摆不满**。第一版只会「随机摆放」，箭头数量接近格子总数（例如 6×6 摆 36 个）时
   反复摆不满，`generate()` 会一个候选都拿不到。AI 补了一套「洋葱式摆放」：按离最近的边有多远
   给格子分层，从内层往外层逆向摆放——一个箭头指向最近的边时，它前方只可能是更外圈的格子，
   而那些箭头会更早被消除，于是 1..行×列 的任意数量都能构造出可解关卡。
   我用 2×2 到 6×6 的全部箭头数量跑了 325 组自检，箭头数量全部正确、求解器复核全部通过。
2. **`CustomSetup._clamp_arrows` 的返回值语义写错了**。它不管有没有变化都返回 `True`，
   和 `set_value()` 文档里说的「有变化才返回 True」矛盾。改成分支各自记录变化、只有真的夹紧
   时才返回 `True`。
3. **测试样例本身是无解的**。我原本用 `(">>", "<.")` 当「被挡得更多」的对照样例，
   可这三个箭头互相挡死、谁也飞不出去，`score()` 返回 -1，用例必然失败；
   换成 `(">v", "<.")` 后分数 0.87，明显高于对照样例的 0.15。

**我做的修改**：界面方面把选关面板加高（528 → 584 像素）、行高从 44 收到 42，自定义入口按钮
按关卡数量动态定位，避免和「返回主菜单」挤在一起；难度按钮复用主色按钮样式表示「当前选中」，
不额外引入状态字段；另外加了「填满」快捷键，免得玩家点 28 次「＋」才能填满 6×6 的棋盘。
测试方面新增 `tests/test_generator.py` 与 `tests/test_setup.py`，并在 `test_session.py`、
`test_ui_smoke.py` 里补了自定义关卡的流程与面板交互用例，用例总数从 70 涨到 133。
（细节见 `docs/test-record.md` 第 7 节与 `docs/screenshots/01c-custom-setup.png`。）

### 10. 精简界面提示文字，并给每一关加上「返回主菜单」

**我提出的要求**：选关界面那行小字只保留键盘提示；自定义关卡面板除了键盘提示以外的小字全部去掉；
另外给每一关（包括自定义关卡）的界面都加上「返回主菜单」，点击后中断本局回到主菜单；
改完自己截图确认，没问题再一起提交。

**AI 的做法**：把选关面板的副标题换成纯键盘提示（数字键 1-9 / C / L）；自定义面板删掉
「随机生成，生成器保证这一关一定有解」「范围 1-25，填满 = 每个格子一个箭头」
「难度（按 best_layout 评分挑候选）」和两行难度说明。因为一下子少了四行文字，
顺手把面板高度从 568 收到 538、重新排了行距，免得面板里出现空洞。
「返回主菜单」做成游戏界面底部按钮行的第三个按钮（重新开始 / 撤销 / 返回主菜单，整行居中），
鼠标点击与 `M` 键都能中断本局，走的是已有的 `Session.back_to_menu()`。

**效果**：界面上只剩操作必需的信息，面板与底部按钮排布都不再有多余留白；
每一关（含自定义关卡）都能一键回到主菜单，本局进度清零，但自定义关卡仍然留在选关列表里可以重玩。

**我做的修改**：一是注意到「填满」按钮原本是挂在那行「范围 1-25…」提示右边，
提示删掉后它会变成孤零零一个按钮，改成右对齐贴在箭头数量那一行下方；
二是补了 5 条用例把这个行为锁住——六个内置关卡与自定义关卡都要暴露该按钮、点击后阶段回到主菜单、
进度（箭头数 / 失误 / 点击次数）清零、`M` 键等价、动画播放期间按钮不响应（避免动画和流程打架）。

## 使用体会

- **AI 最擅长的是把「套路」一次说清**：逆向摆放保证关卡可解、贪心求解器不需要回溯、
  动画期间锁输入，这些都是它直接给出的成熟做法，省掉了大量试错。
- **AI 最容易犯错的地方是「边界」和「统计」**：路径检测的负索引、重复通关的计数、
  测试用例里对棋盘边界的假设，都是它第一次没想周全的地方，需要自己盯住。
- **不要相信没跑过的代码**：51 条用例第一轮就有 3 失败 5 报错，截图第一版就有两处重叠。
  所有结论都以实际运行结果为准。
- **AI 交出来的第一版常常是「跑得起来但边界没想周全」**：自定义关卡里的三处问题——高密度摆不满、
  夹紧函数的返回值语义、拿一个本身就无解的布局当难度对照——都属于这一类。参数范围、边界取值和
  「样例到底成不成立」，还是得自己手算一遍、跑一遍才靠得住。
- **崩溃要从资源生命周期找原因**：`0xC0000005` 这种访问违例通常不是判断逻辑写错，
  而是缓存的对象在被释放之后还在用。「单独跑通过、整包跑崩溃」这种差异，
  往往指向跨会话的状态残留，而不是当前这一步的代码。
